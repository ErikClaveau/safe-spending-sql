# ADR-001: PostgreSQL as the only database engine

> 🇪🇸 Español: [../es/adr/0001-motor-de-base-de-datos.md](../es/adr/0001-motor-de-base-de-datos.md)

**Status:** Accepted
**Date:** 2026-10-01
**Decides:** Erik Claveau
**Related:** ADR-002 (isolation between users), ADR-005 (what the LLM sees: tables or views)

## Context

The assistant answers questions about a user's bank spending by running SQL generated by an LLM. That SQL is not trusted: the model can be wrong or be manipulated, both by the user's question and by text injected in the concepts of the movements. The project's strictest requirement is that the cross-user leak rate be **0** on the adversarial set, and the first layer of defence must hold "even if everything else fails".

Forces at play:

- **Small volume.** 50-200 synthetic users × 12-24 months give fewer than ~500,000 movements. Analytical performance is not a differentiating factor.
- **Isolation imposed by the engine.** The isolation guarantee cannot depend on the generated SQL containing the right filter.
- **Representative evals.** The main metric (execution accuracy) is only valid if measured on the same engine and dialect that would be used in production.
- **Project constraints.** 6 weeks at 5-10 h/week. Docker Compose and GitHub Actions are already decided.
- **Portfolio goal.** Demonstrate credible practices for regulated banking environments.

## Decision

**PostgreSQL** is used in every environment (local, CI and evaluation), with Row-Level Security as the base isolation mechanism. The minimum version is 15, needed for `security_invoker` on views. The exact version is pinned in the Docker Compose image.

**DuckDB is rejected**, also as a test adapter. The `QueryExecutor` port will have a single real adapter (Postgres). Unit tests of components that do not depend on the engine use in-memory doubles, not another database.

## Options considered

### Option A: PostgreSQL

| Dimension | Assessment |
|---|---|
| Isolation | Native RLS: the engine applies the policies to any query, whatever its text |
| Access control | Roles, `GRANT`/`REVOKE`, read-only transactions and `statement_timeout` per role |
| Realism | High; the usual standard in production backends and in banking |
| Complexity | Medium: an extra service in Compose and CI, and known RLS traps |
| Cost | None (official image, self-hosted) |

**Pros**
- Natively covers layers 1, 2 and 4 of the defence (RLS, read-only role, execution limits).
- The evals and adversarial tests run against the same engine that imposes the isolation.
- It is the technology that adds most value in professional environments and builds on the Postgres knowledge I already use at work.

**Cons**
- Learning curve in roles, policies, session variables and view security.
- Traps that can nullify RLS if misconfigured: the table owner skips the policies unless `FORCE ROW LEVEL SECURITY` is set, views run with the owner's permissions unless `security_invoker`, and `SET` without `LOCAL` contaminates pooled connections.
- Integration tests are slower than with an embedded engine.

### Option B: DuckDB

| Dimension | Assessment |
|---|---|
| Isolation | No native RLS or role model; isolation would have to be imposed by rewriting the SQL |
| Access control | Limited; embedded engine without users |
| Realism | Low for a multi-user transactional system |
| Complexity | Low: embedded, no service, a single reproducible file |
| Cost | None |

**Pros**
- Zero operations: ideal for prototypes and fast CI.
- Very fast on analytical queries.

**Cons**
- Isolation would depend entirely on injecting filters with sqlglot into SQL generated by a model under attack. A poorly covered CTE, subquery or `UNION` is a leak.
- Running inside the application process, the generated SQL would have access to file-reading functions, `ATTACH` and extensions with network access, unless explicitly disabled.
- It does not allow running the mandatory RLS test or a representative adversarial set.

### Option C: PostgreSQL in production + DuckDB for tests and evals

**Rejected.** Dialect differences (dates, intervals, casts, rounding) would introduce noise in execution accuracy, and the isolation tests could not run on DuckDB. Maintaining two adapters would consume time without giving a reliable signal.

## Trade-off analysis

The deciding factor is where the isolation guarantee lives. With PostgreSQL it lives in the engine, and the LLM's SQL is treated as untrusted without that compromising other users' data. With DuckDB it lives in the correctness of a SQL rewriter, which is a good second layer but a poor sole layer.

DuckDB's operational simplicity is its real advantage, but it weighs little here: Docker Compose is already decided and a Postgres in GitHub Actions is a standard service container. The effective cost of PostgreSQL is learning to configure RLS correctly, and that learning is one of the project's goals.

## Consequences

**Easier**
- Designing isolation as a property of the engine (ADR-002) instead of a transformation of the SQL.
- Measuring execution accuracy and leak rate under conditions equivalent to production.
- Defending the design in an interview for a regulated environment.

**Harder**
- Correctly configuring and testing roles, policies, session variables and views.
- Integration tests require starting Postgres (Compose locally, service container in CI).

**To revisit**
- ADR-002 becomes conditional: RLS is the main guarantee and rewriting with sqlglot, if added, is defence in depth.
- ADR-005 must assume views with `security_invoker = true` so that the semantic layer respects RLS.
- The data model may need `user_id` denormalised into `transactions` to simplify the policies. Decided in ADR-002.
- This decision would only be reopened if the project needed analysis over volumes PostgreSQL does not handle comfortably, which is outside the expected scope.
