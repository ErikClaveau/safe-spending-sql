# ADR-002: User isolation based exclusively on Row-Level Security

> 🇪🇸 Español: [../es/adr/0002-aislamiento-entre-usuarios.md](../es/adr/0002-aislamiento-entre-usuarios.md)

**Status:** Accepted on 2026-10-05, after the RLS lab (`lab/rls/`) validated the points in the "Acceptance criteria" section
**Date:** 2026-10-01
**Decides:** Erik Claveau
**Related:** ADR-001 (PostgreSQL as the only engine), ADR-005 (what the LLM sees: tables or views)

## Context

The assistant runs LLM-generated SQL on a database holding every user's movements. That SQL is not trusted: the model can be wrong or be manipulated by the user's question or by text injected in the movements' concepts. The requirement is **0 cross-user leaks** on the adversarial set, and isolation must hold even if the other layers fail (classification, prompt and static validation).

After ADR-001, PostgreSQL is the only engine and Row-Level Security (RLS) is natively available. Still to decide:

1. whether RLS is the only isolation mechanism or is combined with rewriting the generated SQL;
2. how the user's identity reaches the policies;
3. what changes the data model needs;
4. which database roles exist and with what permissions;
5. how to verify that isolation stays correctly configured.

## Decision

### Mechanism

Isolation rests **exclusively on RLS**. The SQL generated by the LLM is **not rewritten** to add user filters. Defence in depth comes from independent layers: the LLM does not know the `user_id`, the application role is read-only and sqlglot applies an object allowlist. On top of that comes an automatic check of the RLS configuration in CI.

### Identity propagation

1. The API's authentication layer resolves the `user_id`. It is never taken from the user's question or from the LLM's output. In this project authentication is simulated (out of scope), but the contract is the same.
2. The LLM generates the SQL without knowing the user. The `user_id` column does not appear in the schema shown to it.
3. For each query, the executor:
   - opens an explicit read-only transaction;
   - sets the identity with `SELECT set_config('app.user_id', %s, true)`, with the id as a parameter and never interpolated (the `true` is equivalent to `SET LOCAL`, so the variable dies with the transaction and does not contaminate the connection when it returns to the pool);
   - checks that the variable was set before executing;
   - runs the generated SQL as is and closes the transaction.

### Policies

Every table with user data uses the same policy shape:

```sql
ALTER TABLE transactions ENABLE ROW LEVEL SECURITY;
ALTER TABLE transactions FORCE ROW LEVEL SECURITY;

CREATE POLICY aislamiento_usuario ON transactions
  FOR SELECT TO app_reader
  USING (user_id = NULLIF(current_setting('app.user_id', true), '')::int);
```

- **Tables with RLS:** `users`, `accounts`, `transactions`.
- **Tables without RLS:** `merchants` and `categories`, which are shared catalogs with no personal data.
- **Fail closed:** if the variable is not set, `NULLIF` turns it into `NULL`, the comparison is never true and the query returns 0 rows. The executor's prior check prevents a bug from showing up as a false "you have no movements".
- **`FORCE ROW LEVEL SECURITY`** makes even the table owner subject to the policies.

### Data model

- `transactions` carries a denormalised `user_id`, so that its policy does not depend on a join with `accounts`.
- Consistency is guaranteed in the database with a composite foreign key:

```sql
ALTER TABLE accounts ADD UNIQUE (account_id, user_id);
ALTER TABLE transactions
  ADD FOREIGN KEY (account_id, user_id) REFERENCES accounts (account_id, user_id);
```

- `merchants` contains only companies. Counterparties that are natural persons (Bizum, transfers between individuals) are stored only in `transactions.counterparty`, which is protected by RLS. This is a mandatory rule for the data generator.

### Database roles

| Role | Use | Permissions |
|---|---|---|
| `app_owner` | Migrations; schema owner | DDL. Not used by the API. |
| `app_loader` | Loading synthetic data | `INSERT` and `BYPASSRLS`. Load scripts only, never the API. |
| `app_reader` | The API's only role | `SELECT` only; no `BYPASSRLS`; `default_transaction_read_only = on` and `statement_timeout` set on the role itself. |

All end users share `app_reader` and are distinguished by the session variable, not by Postgres roles.

### Continuous verification

A **configuration test** in CI queries the Postgres catalog and fails if:

- any table with user data does not have RLS enabled and forced (`pg_class.relrowsecurity`, `relforcerowsecurity`);
- any of those tables has no policy for `app_reader` (`pg_policies`);
- any semantic-layer view lacks `security_invoker` (`pg_class.reloptions`);
- `app_reader` has `BYPASSRLS` or is a superuser (`pg_roles`).

## Options considered

### Option A: RLS as the only mechanism + configuration verification (chosen)

**Pros**
- The guarantee lives in the engine and does not depend on the text of the generated SQL.
- A single implementation of the filter: no duplicated logic that can diverge.
- The LLM never needs to know or handle the `user_id`.
- The main risk (an incorrect RLS configuration) is detected automatically in CI.

**Cons**
- If RLS is misconfigured and the configuration test does not cover the case, there is no second isolation-specific barrier.
- Requires mastering the RLS traps: owner, views, session variables with connection pooling.

### Option B: RLS + SQL rewriting with sqlglot as a second layer

**Pros**
- A second independent barrier against an incorrect RLS configuration.

**Cons**
- Correctly rewriting CTEs, subqueries, joins, `UNION` and aliases is complex, and an uncovered case leaves the layer ineffective.
- Duplicates the isolation logic in two places that can diverge.
- Forces reintroducing the `user_id` on the generated SQL's path.
- Introduces execution failures that contaminate execution accuracy.

### Option C: SQL rewriting only

**Rejected.** After ADR-001 it makes no sense to give up a guarantee imposed by the engine in order to depend on a parser processing SQL generated under attack.

## Trade-off analysis

Option B protects against one specific error: RLS misconfigured. But it does so with a fragile and costly mechanism, and shifts the risk instead of removing it. Option A attacks that same error at its origin: it checks deterministically, on every build, that the configuration imposing isolation is still in place. The other layers (LLM without identity, read-only role, sqlglot allowlist, timeouts) provide defence in depth without repeating the filter.

## Consequences

**Easier**
- Writing and reasoning about the generation pipeline: the SQL never contains isolation logic.
- Auditing isolation: all policies have the same shape and their presence is verified in CI.

**Harder**
- The executor must handle transactions and session variables rigorously.
- Every new table with user data needs `user_id`, forced RLS and a policy. The configuration test must include it.

**To revisit**
- **ADR-005:** with `security_invoker`, Postgres checks the base tables' permissions against `app_reader`, which therefore needs `SELECT` on them. That the LLM uses only views cannot be guaranteed by `GRANT`s; the sqlglot allowlist must do it.
- **Data generator:** respect the rule of personal counterparties outside `merchants`.

## Associated tests

1. **Direct RLS, no LLM:** hand-written queries with the variable set to another user return 0 rows of the others'.
2. **Fail closed:** a query without setting `app.user_id` returns 0 rows.
3. **Pool contamination:** after user A's query, a query on the same connection without setting the variable returns 0 rows.
4. **Configuration:** the catalog checks described in "Continuous verification".
5. **Adversarial set:** any row of another user breaks the build.

## Acceptance criteria (RLS lab)

- [x] A policy with `FORCE` prevents the owner from seeing rows without the variable set.
- [x] A view without `security_invoker` behaves as expected and one with `security_invoker` respects RLS.
- [x] `set_config(..., true)` does not persist after the end of the transaction on a reused pool connection.
- [x] An empty or absent variable produces 0 rows.
- [x] `app_reader` cannot write even if it tries to turn off read-only mode inside the transaction. If it can, the block depends on the `GRANT`s; document it. *(It can, before the first query: see results.)*

## Lab results

Run on 2026-10-05 on PostgreSQL 16 (`lab/rls/`, 47 passing tests: 31 for criteria and associated tests, 16 for configuration). The tests connect only as `app_owner` and `app_reader`; the superuser only creates roles and schema, because it bypasses RLS.

| Criterion | Result |
|---|---|
| 1. `FORCE` and owner | `app_owner` sees 0 rows, with and without the variable set: the policy is `TO app_reader`, so no policy applies to the owner and default deny holds. Control with `NO FORCE`: it sees all rows. |
| 2. Views | The view with `security_invoker` filters by user. A view without the option runs as its owner: with `FORCE` it returns 0 rows (the owner has no policy) and with `NO FORCE` it filters everything. |
| 3. Pool | With `set_config(..., true)` the variable does not survive the `COMMIT` and the connection's next transaction sees 0 rows. Control with `false`: it persists and there is a leak. |
| 4. Empty or absent variable | Unset, `''`, `'0'` and `'-1'` give 0 rows. |
| 5. Read-only | See findings. |

### Findings

- **`FORCE` and `security_invoker` are independent layers and each covers the other's failure.** With `FORCE`, a view without `security_invoker` does not expose data, but only because the owner has no policy. If the owner were a superuser or had `BYPASSRLS`, or a future policy included it, the view would expose data. Both are kept, and the configuration check requires `security_invoker` on every view in the schema.
- **Read-only mode is not a barrier by itself.** `app_reader` can leave it with `SET transaction_read_only = off` or `SET TRANSACTION READ WRITE` if it is the first thing the transaction runs; there only the `GRANT`s stop it (`permission denied`). After any query, Postgres rejects it (`transaction read-write mode must be set before any query`), and since the executor's first statement is `set_config('app.user_id', ...)`, the real flow is covered. Decision: the `GRANT`s are the write barrier (`app_reader` only has `SELECT`), and read-only mode is a second layer.
- **`SET default_transaction_read_only = off` is accepted at session level** and would persist on a pooled connection. Writes still fail because of the `GRANT`s. Mitigation: sqlglot must reject any `SET` in the generated SQL and the executor must always open `BEGIN READ ONLY` explicitly.
- **A non-numeric value in `app.user_id`** (`'abc'`) fails closed but with a conversion exception (`invalid input syntax for type integer`), not with 0 rows. It is harmless because the id is set by the authentication layer, never by the user or the LLM.
- **`app_reader` cannot assume another role** (`SET ROLE app_owner` gives `permission denied`).

### Configuration verification

Implemented in `lab/rls/config_checks.py` as catalog queries, with 11 negative controls (the configuration is broken on purpose and the check must fail). Discovery is structural: every table in the schema with a `user_id` column and every view in the schema are checked without maintaining a list by hand, so a new table without RLS breaks the test. It also checks that `app_reader` has a `SELECT` policy on every table with user data.
